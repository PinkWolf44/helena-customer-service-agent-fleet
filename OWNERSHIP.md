# Ownership and Collaboration

Clear attribution is part of the architecture record.

| Work layer | Helena | Market specialist | Infrastructure specialist |
|---|---|---|---|
| Problem and fleet design | Owns | Consulted | Informed |
| SOUL/SKILL architecture | Owns and authors | Supplies local inputs | Not responsible |
| Initial configuration and testing | Owns | Supports with cases | Supports connectivity |
| Ongoing market training | Handles major changes | Owns routine training and small corrections | Not responsible |
| Baselines and incident governance | Owns | Contributes failures and examples | Contributes infrastructure incidents |
| Host and connector availability | Informed/coordinates | Reports failures | Owns |
| Admin-only channel or permission changes | Specifies need | May request | Implements when authorised |

## Attribution principle

Authorship follows the design decision, source transformation, instruction and acceptance judgement—not merely the person or process that clicked an admin control, created a host or executed a prepared change.

The reverse also matters: when a market specialist substantially reorganises files, creates scheduled jobs or repeatedly trains an agent, that contribution should be credited rather than hidden under the original architecture claim.

## Status vocabulary

| Term | Meaning |
|---|---|
| Configured | Behavioural files exist |
| Deployed | Runtime exists on a host |
| Connected | Required integrations are technically available |
| Operational | People use the system in a real workflow |
| Adopted | Use is sustained rather than only tested |

These words are not interchangeable. A deployed agent may never be trained or adopted, and a team-messaging-connected runtime may still lack the inbox and internal-data connections required for customer-service operation.
